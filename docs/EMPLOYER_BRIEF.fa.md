# بخش اول — نمای کلی سیستم و جریان اجرا

## ۱) FileScan چیست؟

FileScan یک **API چندموتورهٔ اسکن بدافزار** برای تحقیق / پایلوت سازمانی است.

کاربر (یا سیستم دیگر) یک فایل می‌فرستد. چند موتور امنیتی — هرکدام از زاویهٔ خودش — فایل را بررسی می‌کنند. در پایان، سیستم یک گزارش واحد با نتیجهٔ نهایی (`verdict`) برمی‌گرداند:

| نتیجه | معنی ساده |
|--------|-----------|
| `clean` | موتورهای قابل‌اتکا چیزی مشکوک ندیدند |
| `suspicious` | نشانه‌های مشکوک هست، ولی قطعی بدافزار اعلام نشده |
| `malicious` | شواهد قوی برای بدافزار |
| `error` | اسکن معناداری انجام نشد (مثلاً همهٔ موتورها قطع بودند) |

### سه جملهٔ کلیدی برای کارفرما

1. سیستم یک **لایهٔ ارکستراسیون** دارد، نه یک اسکنر تکی؛ هر موتور قابل روشن/خاموش و جایگزینی است.
2. هستهٔ تشخیص رایگان و **محلی** است؛ intel ابری (abuse.ch / YARAify) فقط با **هش** کار می‌کند و **خود فایل هرگز به بیرون ارسال نمی‌شود**.
3. خروجی یک گزارش JSON با `verdict` و جزئیات هر موتور است — مناسب دمو، پایلوت، و اتصال بعدی به سامانه‌های سازمانی.

### چه چیزی الان آماده است؟

| مورد | وضعیت |
|------|--------|
| هستهٔ تشخیص رایگان + API پایلوت + دمو UI | آماده |
| موتورهای محلی (ClamAV، YARA، precheck، oletools، LMD، CAPA، FLOSS، pefile) | آماده |
| lookup اختیاری abuse.ch / YARAify (فقط هش) | آماده |
| حساسیت `lenient` / `balanced` / `strict` | آماده |
| آرشیو تودرتو، کش، لیست سفید/سیاه، fuzzy | آماده |
| صف Redis، Grafana، آنتی‌ویروس تجاری پولی | عمداً بعداً |

## ۲) از کجا شروع می‌شود؟ معماری ساده

### دو سرویس اصلی (Docker Compose)

برای پایلوت فقط **دو** سرویس لازم است:

| سرویس | پورت | نقش |
|--------|------|-----|
| **api** | `8001` | FastAPI + Orchestrator + تقریباً همهٔ موتورها داخل همین کانتینر |
| **clamav** | `3310` | آنتی‌ویروس رسمی `clamd` + دیتابیس امضا |

سایر موتورها (YARA، precheck، oletools، LMD، CAPA، FLOSS، pefile) سرویس جدا نیستند؛ داخل همان `api` اجرا می‌شوند.  
abuse.ch و YARAify هم سرویس Compose نیستند؛ فقط در صورت تنظیم کلید، از اینترنت **استعلام هش** می‌گیرند.

```text
[کلاینت / مرورگر / curl]
        │  HTTP روی پورت 8001
        ▼
   [سرویس api]
        │
        ├── موتورهای داخل‌پروسه (YARA، precheck، oletools، …)
        ├── subprocess برای LMD / CAPA / FLOSS (در صورت نصب)
        ├── HTTPS فقط برای هش → abuse.ch / YARAify (اختیاری)
        │
        └── TCP 127.0.0.1:3310 ──► [سرویس clamav / clamd]
```

### نقاط ورود برای کاربر / کارفرما

| آدرس / مسیر | کاربرد |
|-------------|--------|
| `http://127.0.0.1:8001/ui/` | دمو UI برای نمایش به ذی‌نفع |
| `POST /v1/scan` | آپلود فایل و دریافت نتیجهٔ اسکن |
| `GET /v1/scan/{id}` | خواندن نتیجهٔ ذخیره‌شده با شناسه |
| `GET /v1/health` | سلامت سرویس و وضعیت هر موتور |
| `http://127.0.0.1:8001/docs` | Swagger / مستند تعاملی API |

امنیت پایلوت:

- هدر `X-API-Key` (پیش‌فرض دمو: `dev-demo-key`)
- محدودیت نرخ درخواست (rate limit)

### مسیر کد (برای تیم فنی، ولی مفید برای فهم جریان)

```text
کلاینت / UI
  → app/main.py                 (راه‌اندازی FastAPI + UI)
  → app/api/routes.py           (endpointهای /v1/*)
  → app/api/security.py         (API Key + rate limit)
  → app/services/orchestrator.py
  → app/engines/*               (هر موتور)
  → app/services/verdict.py     (جمع‌بندی نهایی)
  → ذخیره JSON در results_dir
```

## ۳) ترتیب دقیق اجرای یک اسکن

جزئیات سطح کد (میانبرها، ترتیب موتورها، اسکن اعضای آرشیو):  
[SCAN_PIPELINE.en.md](SCAN_PIPELINE.en.md)

Endpoint اصلی: `POST /v1/scan` با فایل (`multipart/form-data`) و فیلدهای اختیاری:

- `sensitivity` = `lenient` | `balanced` | `strict` (پیش‌فرض: `balanced`)
- `use_remote_intel` = `true` | `false` (پیش‌فرض: `true` — فقط روی استعلام هش اثر دارد)

### گام‌به‌گام

```text
۱) دریافت فایل از کلاینت
   • نام فایل اجباری است
   • فایل خالی رد می‌شود
   • سقف حجم پیش‌فرض حدود ۳۲ مگابایت
   • چک API Key و rate limit

۲) ذخیرهٔ موقت روی دیسک + سیاست MIME
   • اگر نوع فایل در denylist باشد (یا خارج از allowlist)، اسکن نمی‌شود

۳) Orchestrator شروع می‌کند
   • یک شناسهٔ UUID برای اسکن می‌سازد
   • کپی پایدار فایل را در upload_dir نگه می‌دارد
   • SHA256 (اثرانگشت دقیق) را حساب می‌کند
   • در صورت فعال بودن: ssdeep / tlsh (اثرانگشت تقریبی)
   • نوع MIME را تشخیص می‌دهد

۴) میانبرهای سریع (قبل از موتورهای سنگین)
   • denylist (لیست سیاه هش)  → فوری malicious و پایان
   • allowlist (لیست سفید هش) → فوری clean و پایان
   • cache (نتیجهٔ قبلی همین هش + همین حساسیت) → برگرداندن نتیجهٔ کش
   • fuzzy (شباهت تقریبی به نمونه‌های قبلی)
       اگر شباهت خیلی بالا باشد می‌تواند مثل denylist زودتر تمام کند

۵) اجرای موتورهای محتوا / امضا / رفتار — به‌ترتیب سریال:
     1. precheck
     2. ClamAV
     3. YARA
     4. oletools
     5. LMD
     6. CAPA
     7. FLOSS
     8. pefile
     9. abuse.ch     (اگر use_remote_intel=false → skipped)
    10. YARAify      (اگر use_remote_intel=false → skipped)

۶) اگر فایل ZIP یا TAR باشد
   • استخراج کنترل‌شده (عمق تو در تو محدود، سقف تعداد/حجم اعضا)
   • هشدار مسیرهای خطرناک (مثل ../../)
   • اسکن مجدد هر عضو با موتورهای محلی محتوا
     (precheck، ClamAV، YARA، oletools، LMD، CAPA، FLOSS، pefile)
   • موتورهای ریموت فعلاً فقط روی فایل بیرونی اجرا می‌شوند

۷) جمع‌بندی verdict با توجه به sensitivity
۸) ذخیرهٔ JSON نتیجه + برگرداندن به کلاینت
۹) پاک‌سازی فایل موقت اولیه
```

### چرا ترتیب مهم است؟

- **precheck** سریع و ارزان است؛ زود «پرچم‌های سیاستی» را بالا می‌آورد.
- **ClamAV / YARA / oletools / LMD** شواهد قوی‌تر (سخت) می‌دهند.
- **CAPA / FLOSS / pefile** برای نمونه‌های جدید/بدون امضا مفیدند ولی نویز بیشتری دارند (نرم).
- **abuse.ch / YARAify** در انتها، چون فقط استعلام شبکه روی هش هستند و به محتوای محلی وابسته‌اند نه به ترتیب تحلیل محتوا.

### خروجی تقریبی گزارش

سیستم برای هر اسکن چیزی شبیه این برمی‌گرداند (ساده‌شده):

- شناسهٔ اسکن، وضعیت، verdict نهایی، سطح حساسیت
- اطلاعات فایل: نام، حجم، SHA256، MIME
- لیست موتورها: هر کدام `clean` / `suspicious` / `infected` / `matched` / `skipped` / …
- در صورت وجود: نام تهدیدها، جزئیات، مدت زمان هر موتور

---

## ۴) چگونه نتیجهٔ نهایی ساخته می‌شود؟

موتورها دو دستهٔ مفهومی دارند:

| نوع سیگنال | موتورها | معنی برای کارفرما |
|------------|---------|-------------------|
| **سخت (Hard)** | ClamAV، YARA، LMD، oletools، abuse.ch، YARAify، hashlist، fuzzy | شواهد قوی‌تر؛ معمولاً سریع به `malicious` می‌رسند |
| **نرم (Soft)** | precheck، CAPA، FLOSS، pefile، archive | هشدار / نشانه؛ وزنشان با حساسیت تنظیم می‌شود |

### سطح حساسیت (sensitivity)

| حالت | رفتار به زبان ساده | مناسب برای |
|------|---------------------|------------|
| `lenient` | سیگنال‌های نرمِ تنها معمولاً باعث `malicious` نمی‌شوند | وقتی نمی‌خواهید آلارم زیاد ببینید |
| `balanced` | پیش‌فرض؛ تعادل بین پوشش و نویز | دمو و استفادهٔ روزمرهٔ پایلوت |
| `strict` | حتی مشکوک‌های نرم‌تر هم زودتر به `malicious` می‌رسند | وقتی اولویت «از دست ندادن تهدید» است |

**نکته برای کارفرما:** یک فایل ممکن است از نظر ClamAV تمیز باشد، ولی precheck یا CAPA آن را مشکوک کنند. این تضاد باگ نیست؛ همان ارزش چندموتوره بودن است.

## ۶) توضیح مفصل هر موتور

### ۶.۱) Precheck — بررسی اولیه و «حسّ مشکوک بودن»

**نقش:** اولین فیلتر سریع، قبل از موتورهای سنگین. مثل نگهبان ورودی که هنوز کارت شناسایی را با بانک مرکزی چک نکرده، ولی لباس مشکوک یا اسم عجیب را می‌بیند.

**چه چیزهایی را چک می‌کند؟**

- فایل خالی است؟
- پسوند خطرناک دارد؟ (مثل `.exe`، `.ps1`، `.bat`، `.vbs`، `.js`، …)
- **اسم جعلی / دوبل‌اکستنشن:** مثلاً `invoice.pdf.exe` یا `photo.png.exe` — اسم شبیه سند/عکس، ولی در واقع اجرایی
- **عدم تطابق اسم و محتوا:** پسوند `.jpg` / `.pdf` ولی داخل فایل واقعاً برنامهٔ اجرایی (PE/ELF) است
- **آنتروپی بالا:** محتوای خیلی تصادفی/فشرده/رمزشده — اغلب نشانهٔ پنهان‌کاری یا بسته‌بندی مشکوک
- تشخیص اینکه فایل آرشیو است یا نه (برای مراحل بعدی)

**مثال‌های قابل فهم**

- فایلی با نام `صورتحساب.pdf.exe` → مشکوک
- فایلی با پسوند `.png` که در واقع `.exe` است → مشکوک
- فایل خیلی به‌هم‌ریخته و فشردهٔ غیرعادی → پرچم آنتروپی بالا

**محدودیت مهم**  
Precheck معمولاً به‌تنهایی «این ۱۰۰٪ ویروس است» نمی‌گوید. سیگنال **نرم** است؛ به بقیهٔ موتورها کمک می‌کند و با `sensitivity` وزن می‌گیرد.

**چرا برای کارفرما مهم است؟**  
خیلی از حملات مهندسی اجتماعی دقیقاً با اسم جعلی و فایل «به‌ظاهر بی‌ضرر» شروع می‌شوند؛ precheck همین لایه را پوشش می‌دهد.

---

### ۶.۲) ClamAV — آنتی‌ویروس کلاسیک

**نقش:** همان چیزی که مردم معمولاً با شنیدن «آنتی‌ویروس» تصور می‌کنند: دیتابیس بزرگ امضاهای ویروس‌های شناخته‌شده.

**چطور کار می‌کند (ساده ولی دقیق)**

- ClamAV یک سرویس جدا (`clamd`) است؛ همیشه روشن می‌ماند و امضاها را در حافظه نگه می‌دارد.
- API فایل را از طریق شبکهٔ داخلی (TCP) برایش می‌فرستد و جواب می‌گیرد.
- از ابزار یک‌بارمصرف `clamscan` برای هر فایل استفاده نمی‌کنیم؛ روش production-مانند است.

**نتیجه‌های معمول**

- پیدا کردن امضا → `infected` + نام تهدید (مثلاً `Eicar-Test-Signature`)
- پیدا نکردن → `clean` از دید این موتور
- قطع بودن سرویس → `error` / unhealthy در `/v1/health`

**مثال**  
فایل تست استاندارد EICAR را معمولاً هم ClamAV و هم YARA تشخیص می‌دهند → verdict نهایی `malicious`.

**نوع سیگنال:** سخت — برای تهدیدهای شناخته‌شده بسیار قابل اتکا.  
**نکته:** ویروس کاملاً جدید (zero-day) ممکن است هنوز در دیتابیس نباشد؛ برای همین موتورهای دیگر لازم‌اند.

---

### ۶.۳) YARA — قوانین و الگوهای اختصاصی

**نقش:** به‌جای فقط «اسم ویروس شناخته‌شده»، دنبال **الگو** می‌گردد: تکه‌متن، بایت‌های خاص، ترکیب نشانه‌ها.

مثل کارآگاهی که می‌گوید: «اگر این سه نشانه با هم دیده شد، مشکوک/بدافزار است» — حتی اگر آنتی‌ویروس هنوز اسمی برایش نداشته باشد.

**چه چیزهایی را پوشش می‌دهد؟**

- قوانین خود پروژه (مثلاً تست EICAR، الگوهای اسکریپت مشکوک)
- قوانین community که در `rules/yara/` نگه داشته می‌شوند
- نمونه‌ها: وب‌شل PHP، PowerShell مشکوک، الگوهای ماکرو، رشته‌های شناخته‌شدهٔ بدافزار

**نتیجه**

- برخورد سخت (مثلاً تگ malware / شدت بالا) → معمولاً به سمت `malicious`
- برخورد نرم‌تر → `suspicious`

**نوع سیگنال:** سخت.  
**مزیت برای کارفرما:** قوانین را می‌شود برای محیط خودتان سفارشی کرد (مثلاً الگوهای خاص سازمان).

---

### ۶.۴) Oletools — اسناد Office و ماکرو

**نقش:** بازرس مخصوص Word / Excel / فایل‌های Office.

خیلی از حملات سازمانی با ایمیل و پیوست `.doc` / `.xls` شروع می‌شوند. ظاهر سند عادی است؛ داخلش ماکرو یا اسکریپت مخرب است.

**چه می‌پرسد؟**

- آیا ماکرو دارد؟
- آیا ماکرو کار خطرناک می‌کند؟ (اجرای دستور سیستم، دانلود فایل، ارتباط شبکه، …)

**مثال**  
سند «فیش حقوقی.doc» که با باز شدن، بدون اطلاع کاربر یک اسکریپت اجرا می‌کند.

**نوع سیگنال:** سخت.  
**نکته:** برای فایل‌های غیر Office معمولاً حرف زیادی برای گفتن ندارد (و ممکن است skip شود).

---

### ۶.۵) LMD (Linux Malware Detect) — بدافزار لینوکس و وب

**نقش:** تمرکز روی دنیای سرور و وب — جایی که آنتی‌ویروس دسکتاپ کلاسیک همیشه بهترین پوشش را ندارد.

**نمونه‌های هدف**

- فایل‌های PHP آلوده روی هاست
- وب‌شل / درب پشتی (backdoor)
- بدافزار مخصوص لینوکس

**مثال**  
یک `shell.php` که مهاجم روی سایت آپلود کرده تا بعداً دستور اجرا کند.

**نوع سیگنال:** سخت.  
**نکتهٔ عملی:** اگر باینری LMD در محیط نصب نباشد، این موتور `skipped`/`unavailable` می‌شود و بقیهٔ سیستم کار می‌کند. یعنی وابستگی شکننده نیست.

---

### ۶.۶) CAPA — «این برنامه چه کارهایی بلد است؟»

**نقش:** به‌جای پرسیدن «اسم ویروست چیست؟»، می‌پرسد «چه قابلیت‌هایی داری؟»

این برای بدافزارهای **جدید** خیلی مهم است: ممکن است هنوز در هیچ دیتابیس امضایی نباشند، ولی رفتارشان لو برود.

**نمونه‌های قابلیت**

- ثبت کلیدهای کیبورد (keylogging)
- ارتباط مخفی با اینترنت / سرور فرمان‌وکنترل
- رمزنگاری فایل‌ها
- ماندگاری در سیستم (persistence)
- تغییر تنظیمات حساس ویندوز

**مثال**  
یک `.exe` ناشناس که ClamAV آن را نمی‌شناسد، ولی CAPA می‌گوید قابلیت ارتباط شبکه + مخفی‌کاری دارد → مشکوک.

**نوع سیگنال:** نرم.  
**چرا نرم؟** بعضی برنامه‌های مشروع هم قابلیت‌های قوی دارند (مثلاً ابزارهای IT). برای همین نتیجهٔ CAPA را با احتیاط و همراه با بقیه می‌خوانیم.

---

### ۶.۷) FLOSS — استخراج متن‌های مخفی‌شده

**نقش:** خیلی از بدافزارها متن‌های مهم را قاطی می‌کنند یا رمز می‌کنند تا در نگاه اول دیده نشوند: آدرس سرور، دستورات، کلیدها، مسیر فایل‌ها.

FLOSS تلاش می‌کند این رشته‌ها را **استخراج و آشکار** کند.

**مثال‌های قابل فهم**

- پیدا شدن آدرس یک دامنهٔ مشکوک فرمان‌وکنترل
- پیدا شدن دستورات PowerShell مخفی داخل باینری
- رشته‌هایی که نشان می‌دهد فایل برای باج‌افزار یا سرقت اطلاعات آماده شده

**نوع سیگنال:** نرم.  
**ارزش برای کارفرما:** حتی وقتی «اسم ویروس» نداریم، سرنخ‌های متنی برای تحلیل‌گر انسانی یا قوانین بعدی YARA بسیار ارزشمند است.

---

### ۶.۸) Pefile — ساختار فایل‌های ویندوزی (EXE/DLL)

**نقش:** به «ساختمان» فایل اجرایی ویندوز نگاه می‌کند، نه به داستان محتوا به‌صورت متنی.

مثل بازرسی اسکلت یک ساختمان: ممکن است ظاهر نما عادی باشد، ولی اسکلت غیرعادی باشد.

**چه نشانه‌هایی را می‌بیند؟**

- دادهٔ اضافی چسبیده به انتهای فایل (overlay) — گاهی محل مخفی کردن payload
- بخش‌هایی که هم قابل‌نوشتن و هم قابل‌اجرا هستند (W+X) — الگوی مشکوک در بعضی بسته‌بندها
- ناهنجاری در منابع / ساختار PE

**مثال**  
EXEای که ساختارش شبیه فایل‌های packشدهٔ مشکوک است، حتی اگر امضای ویروس نداشته باشد.

**نوع سیگنال:** نرم.  
**محدودیت:** روی فایل‌های غیر ویندوزی (مثلاً PDF خالص یا تصویر واقعی) معمولاً کاری ندارد یا رد می‌شود.

---

### ۶.۹) Abuse.ch (MalwareBazaar) — «قبلاً جایی دیده شده؟»

**نقش:** استعلام از یک پایگاه عمومی بزرگ نمونه‌های بدافزار.

**نکتهٔ حیاتی حریم خصوصی**  
فقط **SHA256** (اثرانگشت) فرستاده می‌شود. **محتوای فایل آپلود نمی‌شود.**  
برای کارفرما این جمله مهم است: «فایل محرمانهٔ سازمان به اینترنت نمی‌رود؛ فقط پرسیده می‌شود این اثرانگشت قبلاً به‌عنوان بدافزار ثبت شده یا نه.»

**مثال**  
همین هش قبلاً در MalwareBazaar به‌عنوان تروجان ثبت شده → تقریباً قطعی `malicious`.

**نوع سیگنال:** سخت.  
**اختیاری:** نیاز به Auth-Key رایگان از https://auth.abuse.ch/  
بدون کلید، موتورهای محلی همچنان کار می‌کنند؛ فقط این استعلام از کار می‌افتد.

**کنترل در هر اسکن:** با `use_remote_intel=false` می‌توان برای یک فایل خاص کاملاً local-only اسکن کرد.

---

### ۶.۱۰) YARAify — قوانین جامعه روی همان هش

**نقش:** مکمل abuse.ch. می‌پرسد آیا جامعهٔ امنیتی برای این هش قانون YARA یا تشخیص مرتبط ثبت کرده است یا نه.

**شباهت با abuse.ch**

- فقط هش
- فایل ارسال نمی‌شود
- اختیاری / نیاز به کلید (معمولاً همان Auth-Key abuse.ch)

**تفاوت مفهومی**

- abuse.ch بیشتر «این نمونه در پایگاه بدافزار هست؟»
- YARAify بیشتر «برای این هش، قانون/مچ جامعه وجود دارد؟»

**نوع سیگنال:** سخت.

---

## ۷) قابلیت‌های کمکی (موتور نیستند، ولی مهم‌اند)

### ۷.۱) Allowlist / Denylist (لیست سفید و سیاه سازمانی)

| لیست | معنی |
|------|------|
| **Denylist** | این هش از قبل بد شناخته شده → فوری `malicious` بدون اسکن کامل |
| **Allowlist** | این هش مورد اعتماد سازمان است (مثلاً نصب‌کنندهٔ داخلی) → فوری `clean` |

**فایده برای کارفرما:** سیاست سازمانی را بدون تغییر موتورها اعمال می‌کند.

### ۷.۲) Cache (کش نتیجه)

اگر همان فایل (همان SHA256) با همان تنظیمات حساسیت قبلاً اسکن شده باشد، نتیجهٔ قبلی برمی‌گردد.

**فایده:** سرعت بالاتر برای فایل‌های تکراری، فشار کمتر روی موتورها.

### ۷.۳) Fuzzy matching (شباهت تقریبی)

گاهی مهاجم فقط چند بایت فایل را عوض می‌کند تا هش دقیق عوض شود.  
Fuzzy با الگوریتم‌هایی مثل ssdeep / tlsh می‌گوید: «این فایل خیلی شبیه نمونهٔ بد قبلی است.»

- شباهت خیلی بالا → می‌تواند مثل denylist عمل کند
- شباهت متوسط → مشکوک

### ۷.۴) Archive scanner (اسکن داخل فشرده)

بدافزار اغلب داخل ZIP پنهان می‌شود.

سیستم:

- ZIP/TAR را با محدودیت‌های امنیتی باز می‌کند (عمق تو در تو، سقف حجم، سقف تعداد فایل)
- مسیرهای خطرناک مثل `../../` را هشدار می‌دهد
- اعضای داخل را دوباره با موتورهای محلی محتوا اسکن می‌کند

**نکته:** lookupهای ریموت (abuse.ch / YARAify) فعلاً روی اعضای داخل آرشیو تکرار نمی‌شوند؛ روی فایل بیرونی هستند.

---

## ۸) چرا چند موتور؟ (جدول تهدید → پوشش)

| سناریوی واقعی | کدام موتور(ها) کمک می‌کنند؟ |
|---------------|------------------------------|
| ویروس شناخته‌شده / نمونهٔ تست EICAR | ClamAV، YARA، گاهی abuse.ch |
| سند Office با ماکرو مخرب | oletools (+ گاهی YARA) |
| فایل با اسم جعلی (`عکس.jpg.exe`) | precheck |
| تصویر/PDF جعلی که در واقع EXE است | precheck |
| بدافزار خیلی جدید بدون امضا | CAPA، FLOSS، YARA، pefile |
| PHP آلوده روی سرور وب | LMD، YARA |
| نمونهٔ قبلاً دیده‌شده در اینترنت | abuse.ch، YARAify |
| ویروس داخل ZIP تو در تو | archive + موتورهای محلی روی اعضا |
| نسخهٔ کمی تغییرکردهٔ بدافزار قبلی | fuzzy |
| نصب‌کنندهٔ رسمی سازمان | allowlist |

**جمع‌بندی برای کارفرما:**  
یک موتور همه را نمی‌گیرد. ترکیب موتورهای **سخت** (اطمینان) و **نرم** (پوشش نمونه‌های جدید) با سطح حساسیت قابل تنظیم، منطق اصلی FileScan است.

---

## ۹) اصول طراحی که برای کارفرما مهم است

| اصل | معنی ساده |
|-----|-----------|
| **Pluggable** | موتور جدید = افزودن یک آداپتر؛ API کلی عوض نمی‌شود |
| **Local-first** | پایلوت بدون سرویس پولی کار می‌کند |
| **Privacy-aware** | به abuse.ch / YARAify فقط هش می‌رود، نه فایل |
| **Never execute** | فایل‌ها اجرا نمی‌شوند؛ فقط اسکن ایستا |
| **Sync MVP** | اسکن فعلی همزمان است؛ صف ناهمزمان (Redis) فاز بعدی است |

## ۱۰) اجرا برای دمو / ارائه

```bash
cp -n .env.example .env
# اختیاری: FILESCAN_ABUSECH_AUTH_KEY را از https://auth.abuse.ch/ بگذارید
docker compose up --build -d
```

بعد از بالا آمدن:

| مورد | مقدار |
|------|--------|

```bash
curl -sS -H "X-API-Key: dev-demo-key" \

  -F "sensitivity=balanced" \
  http://127.0.0.1:8001/v1/scan
```

## ۱۱) جمع‌بندی یک‌صفحه‌ای برای پایان ارائه

1. **FileScan** فایل را می‌گیرد و چند بازرس امنیتی مستقل را روی آن اجرا می‌کند.  
2. **ورودی:** API یا دمو UI روی پورت `8001`؛ پشت صحنه Orchestrator ترتیب کار را مدیریت می‌کند.  
3. **موتورهای سخت** (ClamAV، YARA، oletools، LMD، intel هش) اطمینان می‌دهند.  
4. **موتورهای نرم** (precheck، CAPA، FLOSS، pefile) پوشش نمونه‌های جدید و ترفندهای اسم/ساختار را بالا می‌برند.  
5. **حساسیت** مشخص می‌کند سازمان چقدر سخت‌گیر باشد.  
6. **حریم خصوصی:** در intel بیرونی فقط هش می‌رود.  
7. خروجی یک **گزارش واحد** است که هم برای دمو به کارفرما قابل فهم است، هم برای اتصال بعدی به سامانهٔ سازمانی.
